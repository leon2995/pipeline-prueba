# Criterios: cuenta-agente (T1)

Riesgo: **alto**. Credenciales y permisos: cuenta de GitHub propia del agente (`talos-bot`), token, CODEOWNERS y protección de ramas. Plan aprobado por Leonardo tras HUMAN en la auditoría del plan (dos vueltas en `fail`), con sus decisiones: token con `--insecure-storage` fuera del repo, herramienta PowerShell denegada, regla permanente para los cambios en rutas de gobierno y orden de pasos a, b, d, e, c, f, g. Doble auditor (Claude y Codex), merge a `staging` y a `main` por Leonardo.

**Modelo de amenaza: errores del agente, no ofuscación deliberada.** Los controles frenan que el agente, por costumbre o descuido, mergee o apruebe un PR de gobierno, vuelva a la cuenta de Leonardo, trabaje sin la identidad de `talos-bot` o imprima una credencial. No cubren que el agente use a propósito las credenciales de Leonardo que siguen en la máquina (keyring de `gh` y Git Credential Manager). El token de `talos-bot` vive en `~/.talos-gh/hosts.yml`, un archivo de texto fuera del repo: los procesos hijos (por ejemplo Codex) heredan `GH_CONFIG_DIR` y podrían leerlo si lo buscaran; se declara y no se persigue. El control efectivo sobre los PRs de gobierno pasa a ser el servidor (CODEOWNERS y protección de ramas); el hook queda como primera barrera.

- **C1.** `.github/CODEOWNERS` asigna a `@leon2995` exactamente las reglas de `.claude/rutas-gobierno.txt`, traducidas (`**/X/` → `X/`, `**/X` → `X`, `X/` → `/X/`, `X` → `/X`). El comparador de `scripts/test-hooks.sh` falla si no coinciden y se prueba a sí mismo con variantes: falta una regla, sobra una, otro dueño, dos dueños, `/.claude/` anclado por error, archivo ausente y CODEOWNERS vacío fallan; CRLF pasa. Exige al menos una regla y que cada línea tenga exactamente el dueño `@leon2995`. Rechaza reglas `**/X` y `**/X/` con una barra interna (su traducción cambiaría de cobertura), igual que el hook, y lo documenta el encabezado de `rutas-gobierno.txt`. Diferencia declarada: CODEOWNERS distingue mayúsculas y el hook no.
- **C2.** Un job de CI llamado `hooks` corre `bash scripts/test-hooks.sh` en `ubuntu-latest` en cada PR y en cada push a `feat/**` y `fix/**`, y la corre también con mawk (lo instala si la imagen no lo trae). Evidencia antes del PASS: la corrida del push de la rama, en verde, con su URL. *Corrección durante la implementación: el plan suponía que en `ubuntu-latest` awk es mawk; la corrida mostró GNU Awk 5.2.1, así que se agregó el paso con mawk.*
- **C3.** `guard-commands.sh` bloquea, con casos en la suite:
  - exposición de credenciales: cualquier comando que mencione `GH_TOKEN`, `GITHUB_TOKEN`, un prefijo de token de GitHub (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), `settings.local` (salvo `settings.local.example`), `.talos-gh` o `hosts.yml`; `gh auth token`; `gh auth status` con `-t`/`--show-token`; `gh auth git-credential`; `git credential fill|approve|reject`; y `env`, `printenv`, `set`, `export`, `export -p`, `declare -p`/`-x` y `typeset` sin argumentos en cualquier segmento;
  - cambio de identidad: `gh auth login|logout|switch|refresh|setup-git`; cualquier comando que nombre `GH_CONFIG_DIR` o `GIT_CONFIG_*`; `git -c ...credential...` y `git config ... credential`;
  - aprobación: `gh pr review` con `--approve` o `-a` (el agente nunca aprueba).
  Permite `gh auth status` sin `-t`, `gh pr review` con comentario o pedido de cambios, y `gh pr merge --help`.
- **C4.** Identidad fail-closed, activable: si existe `.claude/identidad-agente.txt` (junto a los hooks, con el login esperado, `talos-bot`), el hook bloquea `git commit`, `git push`, `gh pr create|merge|review|comment|edit|close|reopen|ready` y `gh api` de escritura (método distinto de GET, `-f`/`-F`/`--field`/`--raw-field`/`--input` o `graphql`) cuando falta `GH_CONFIG_DIR` o `GIT_CONFIG_COUNT`, cuando `GIT_AUTHOR_NAME` o `GIT_COMMITTER_NAME` no es el login esperado, o (en `git push` y `gh`) cuando `gh api user --jq .login` no lo devuelve. En `git push` exige además (*intento 3*) la configuración exacta de la plantilla (`GIT_CONFIG_COUNT`=2, `GIT_CONFIG_KEY_0/1`, `GIT_CONFIG_VALUE_0` vacío y `GIT_CONFIG_VALUE_1`=`!gh auth git-credential`), que `git config --get-urlmatch credential.helper https://github.com` devuelva `!gh auth git-credential`, y que el remoto sea HTTPS de github.com sin usuario (`--repo` no está soportado). El mensaje dice que falta la identidad de `talos-bot` (`settings.local.json`). Sin el archivo no se exige (arranque); con el archivo vacío se bloquea. T1 no crea el archivo. La suite corre sobre copias del hook, así que su resultado no depende de que el archivo exista en el repo.
- **C5.** `.claude/settings.local.json` está en `.gitignore`. `.claude/settings.json` deniega la herramienta `PowerShell`, y `Read`, `Edit` y `Write` sobre `./.claude/settings.local.json`, `**/.claude/settings.local.json` y `~/.talos-gh/**`. Hay una plantilla `.claude/settings.local.example.json` sin secretos: `GH_CONFIG_DIR` (ruta a `~/.talos-gh`), `GIT_CONFIG_COUNT` = `"2"`, `GIT_CONFIG_KEY_0`/`_1` = `credential.https://github.com.helper`, `GIT_CONFIG_VALUE_0` = `""` y `GIT_CONFIG_VALUE_1` = `"!gh auth git-credential"`, y autor y committer `talos-bot` con el email noreply de GitHub. Ningún token vive en el repo ni en variables de entorno.
- **C6.** `CLAUDE.md` refleja el flujo nuevo: las cuentas (`talos-bot` colaboradora con escritura; `leon2995` dueño y code owner); la regla permanente de que los cambios en rutas de gobierno los implementa el CTO (pruebas e implementación), compensada con el commit de pruebas primero, la mutación contra `staging`, los dos auditores y la aprobación de Leonardo como code owner; la Fase 4 (los PRs los abre `talos-bot`; los de gobierno a `staging` los aprueba y mergea Leonardo; los de `staging` a `main` los abre `talos-bot` y Leonardo los aprueba y mergea); la lista de OK explícito dice que el servidor exige la aprobación del code owner; qué procesos pueden llegar a las credenciales; y que la herramienta PowerShell está denegada.
- **C7.** `SETUP.md` explica, en el orden a, b, d, e, c, f, g, cómo crear y conectar `talos-bot`: cuenta machine creada por una persona; colaboradora con escritura; token classic con `repo`, `read:org` y `workflow` (*cambio del intento 3, aprobado por Leonardo: `gh auth login` rechaza un token pegado sin `repo` y `read:org`, y `public_repo` no cuenta como `repo`; `repo` solo alcanza los repos donde `talos-bot` es colaboradora*); login interactivo con `--insecure-storage` en `~/.talos-gh` (nunca `echo` del token ni pegarlo en el chat); un campo "Vence: AAAA-MM-DD (completar en el paso c)" con el recordatorio de rotarlo 14 días antes; verificación de las dos identidades (`gh api user --jq .login` con y sin `GH_CONFIG_DIR`) y del helper (`git config --show-origin --get-regexp '^credential\..*helper$'` y `git config --get-urlmatch credential.helper https://github.com`; *corrección del intento 2, pedida por el auditor y aprobada por Leonardo: el `--get-all credential.helper` original no lee la clave `credential.https://github.com.helper`*); los comandos `gh api` del paso e (PATCH `required_pull_request_reviews` con `-F`; PATCH `required_status_checks` con un JSON que trae `secrets` y `hooks` con `app_id` 15368 y `strict` en false; y un GET que verifica los cinco campos), con `main` en 1 aprobación, code owners, Dismiss stale approvals y `enforce_admins`, y `staging` en 0 aprobaciones y code owners; volver a correr el CI de los PRs abiertos después del paso e; la alternativa si en `staging` el code owner no bloquea con 0 aprobaciones; y en el paso f fusionar con `settings.local.json` si ya existe y reiniciar la sesión.

Verificación posterior al PASS (fuera de los criterios del auditor): pasos a a g de Leonardo, incluidos los dos PRs de prueba.
