# Criterios: remoto-git-push (PR corto de gobierno, paso f)

Riesgo: **medio**. Cambia cómo C4 de `guard-commands.sh` lee el remoto de `git push` con la identidad de `talos-bot-leon` activa. Sale de dos hallazgos de la auditoría del intento 3 de cuenta-agente (PR #6): la media del falso positivo y la alta de Codex sobre las opciones con valor. **Alcance estricto, por decisión de Leonardo:** quitar las redirecciones y el texto entre comillas antes de leer el remoto de `git push`, y leer bien las opciones de `git push` que llevan valor (`-o`/`--push-option`, `--receive-pack`/`--exec`, `--repo`). Nada más.

**Proceso ligero, excepción aprobada por Leonardo** para este PR, T2 y T3: una ronda del auditor Claude, sin Codex ni JEV, y Leonardo aprueba como code owner. Su razón: con la protección de code owners activa (paso e), ningún cambio de gobierno entra sin su aprobación. Este PR lo abre `talos-bot-leon` y es el PR de gobierno de la verificación del paso f: tiene que quedar bloqueado hasta la aprobación de Leonardo.

**Modelo de amenaza: errores del agente, no ofuscación deliberada.** Los límites que siguen documentados en el hook (separadores `;`, `&` o `|` dentro de comillas, `bash -c`, remoto por defecto `origin` sin mirar `pushRemote`) quedan fuera de alcance.

- **C1. Redirecciones.** Antes de partir el comando en segmentos, C4 normaliza las redirecciones igual que `analizar_git` (`2>&1`, `>&2`, `&>`, `>|`), y al leer los argumentos de `git push` salta los tokens de redirección (`>archivo`, `2>/dev/null` y el operador suelto con su archivo). Con la identidad completa pasan `git push 2>&1 | tail -3`, `git push >/dev/null` y `git push origin feat/x 2>/dev/null`.
- **C2. Texto entre comillas.** Para decidir si un segmento es un `git push`, C4 mira el segmento sin el texto entre comillas. Un `git push` escrito dentro de un `-m` o un `--title` no cuenta como push. Con la identidad completa pasan `git commit -m "docs: el hook revisa git push antes del PR"` y `gh pr create --title "T4: git push con helper" --body-file b.md`. Los argumentos del push real se leen respetando comillas, con `xargs`, como el bloque de `gh pr merge`. Un remoto entre comillas se sigue leyendo: `git push "git@github.com:o/r.git" feat/x` y `git push "https://leon2995@github.com/o/r.git" feat/x` se bloquean. Si no se pueden leer (comillas sin cerrar), se bloquea.
- **C3. Opciones con valor.** El remoto es el primer argumento posicional después de `push`. Se saltan los valores de `-o`, `--push-option`, `--receive-pack` y `--exec`, en la forma separada y con `=`, y los de un grupo de flags cortos que termina en `o` (`-uo x`). Con `-ox`, el valor va pegado. Cada caso con un valor `https://github.com/...` seguido de un remoto SSH se bloquea con "no es HTTPS". Pasan `git push -o ci.skip origin feat/x` y `git push --push-option=ci.skip origin feat/x`.
- **C4. `--repo`.** Deja de bloquearse. Igual que en git, el remoto es el argumento posicional si existe; si no, el valor de `--repo` (separado o con `=`); si no, `origin`. Pasa `git push --repo=origin`. Se bloquean `git push --repo git@github.com:o/r.git` y `git push --repo=https://leon2995@github.com/o/r.git`. `git push --repo=origin feat/x` toma `feat/x` como remoto y se bloquea con "no es HTTPS", como falla git.
- **C5. Sin regresiones.** Los casos existentes de C4 siguen pasando (el de `--repo` cambia su motivo a "no es HTTPS"). El push a `main`, el push forzado y el borrado siguen en `analizar_git`, que no cambia. Suite en verde local y en CI (gawk y mawk). La mutación contra `staging` falla en los casos nuevos.
- **C6.** El encabezado del hook deja de listar los límites que este PR cierra (opciones con valor leídas como remoto y el falso positivo) y conserva los demás. *Después de la ronda de auditoría:* suma los dos límites que marcó el auditor fuera del modelo de amenaza y del alcance (comillas anidadas, prefijos de opciones largas). El punto 4 del paso g de `SETUP.md`, que describía el falso positivo, pasa a ser la verificación de que un push normal pase.
